### 指示の手順から変えたところ

- **HILTI exp04 の取得元**：`download_hilti2022.sh` の S3 の URL は `AccessDenied`（403）だった。HILTI の公式ページは Hugging Face（`Hilti-Research/hilti-slam-challenge-2022`）にリンクしているので、そこから同じファイル（10,469,762,246 バイト、sha256 `c650f16f30744d2edff15dcd722a7f21ae0f8868809a3c8863cedd0fc5108799`。スクリプトが記録する raw sha256 と同じ）を、スクリプトが期待する場所に置いてからスクリプトを `--drop-bag1` 付きで実行した。キャリブレーションの zip も S3 で取れないため、Hugging Face の calibration_files の yaml から作った（ベンチには使わない）。変換後の bag は sqlite3、13.46 GB、76,611 メッセージ、長さ 125.814128037 秒、/hesai/pandar 1258、/alphasense/imu 50,198。
- **MID-360**：指示どおり `download_mid360_robot_public_dataset.py` で取得（sha256 `f8f89eeb…` を検証済み）。/livox/lidar 2772、/livox/imu 55,435、277.17 秒。
- **FetchContent の取得元**：GitHub のアーカイブ URL がこの環境では 403 だったため、同じタグを git で取得して `FETCHCONTENT_SOURCE_DIR_*` で渡した（Eigen は gitlab の tarball をそのまま使用）。ビルドのオプションは指示どおり（Release、`-DBUILD_TESTING=OFF -DRKO_LIO_BUILD_ROS=ON -DRKO_LIO_FETCH_CONTENT_DEPS=ON`、テスト用は `-DBUILD_TESTING=ON -DRKO_LIO_BUILD_TESTS=ON`）。ビルドの高速化に ccache を使った（同じ入力から同じ出力を返すだけなので、バイナリは変わらない）。
- **python3**：この VM のイメージは `/usr/bin/python3` が 3.13 だったので、ROS 2 Jazzy に合わせて 3.12 に切り替えた。
- **slam のリポジトリ**：develop（9cc828b、rko_lio サブモジュールは 80f3c1c）。サブモジュールの clone に失敗したので、ローカルの rko_lio から 80f3c1c をそのまま書き出した。Dockerfile と同じく `--packages-up-to lidarslam rko_lio` を Release でビルドし、実行時は rko_lio だけを各計測用ビルド（下記の 80f3c1c・f6b0425・734d54f）でオーバーレイした。`ros2 pkg prefix rko_lio` がオーバーレイ側を指すことを確認済み。
- **単独ブランチ perf/parallel-deskew（f089726）**：積み上げ版の 12cc517 と git の tree が完全に同じ（同じソース）なので、md5 と速度は 12cc517 のビルドで測った。テスト用ビルドは f089726 で別に作って実行した。

- 比は「B の中央値 / A の中央値」。各組の比（B/A）の中央値も併記する。

### 5.1 バックエンドは律速になっていないか

別に 1 回ずつ、1 秒ごとに各プロセスの CPU 時間（/proc/<pid>/stat）を記録した（`data/pipe/diag_cpu_*.csv`）。

| | offline_node（フロントエンド） | graph_based_slam_node |
|---|---|---|
| f6b0425 | CPU 159.3 秒 / 47 秒（平均 3.39 コア、最大 3.61） | CPU 4.2 秒 / 48 秒（平均 0.09 コア、最大 0.21） |
| 734d54f | CPU 141.5 秒 / 42 秒（平均 3.37 コア、最大 3.65） | CPU 4.2 秒 / 44 秒（平均 0.10 コア、最大 0.24） |

- バックエンドは 1 コアの 1 割程度しか使っておらず、律速になっていない。壁時計はフロントエンドの所要時間 + 起動と終了の約 3 秒で決まっている。
- ただしこのベンチは `--skip-map-save` で、`lidarslam_competitive_v2.yaml` はループ探索を切っている（`range_of_searching_loop_closure: 0.0`）。地図の保存を有効にした場合は見ていない（ループ閉じ込みを有効にした場合は 10 章）。また壁時計はフロントエンドのダンプが出た時点で止まるので、バックエンドに遅れがあっても wall_seconds には出ない（上の CPU 量から、遅れはないと判断した）。

## 6. 追加の高速化（このセッション、f6b0425 の上に 1 変更 1 コミット）

perf（cpu-clock、全スレッド）で f6b0425 を見ると、CPU サンプルの 49% がキャッシュ付きの `get_closest_neighbor` で、その 48% がボクセルの点を読む命令の直後に集中していた（`data/perf/`）。近傍探索ではメモリ待ちが大きいと判断した。

### 6.1 採用：f4a6547「Prefetch the cached voxel points before the ICP neighbour search」

- キーポイントが前回と同じボクセルにいるとき、キャッシュにある近傍ボクセルの点の先頭（最大 3 キャッシュライン、点数に合わせる）を、探索を始める前にまとめてプリフェッチする。
- 変わらない理由：プリフェッチはヒントで、読むボクセル・点・順序・演算は何も変わらない。GCC/Clang は `__builtin_prefetch`、MSVC（x86/x64）は `_mm_prefetch`、それ以外は何もしない。
- 効果：f6b0425 比 0.949（3 組）。プリフェッチ後、点の読み込みでの停止は関数内サンプルの 48% → 14% に減った。

### 6.2 採用：734d54f「Sum the ICP systems in place instead of passing tuples through the tree」

- 決定的リダクションは、6×6 の H・b・スカラー 3 つのタプル（360 バイト）を葉と結合のたびに値渡しでコピーしていた。`parallel_deterministic_reduce` の Body 形式に替え、和を Body の中でその場で足す。
- 変わらない理由：分割と結合の木は同じ（粒度 1 の simple_partitioner で葉は 1 点ずつ）。葉は「ゼロ + その点の系」、結合は「左の和 += 右の和」で、元と同じ足し算を同じ順に行う。対応のない点は何も足さないが、元もゼロを足していただけで、和は +0 から始まり +0 を足しても変わらない（-0 になることもない）。1 点ぶんの系は元と同じ式で作る。
- 効果：f4a6547 比 0.965（3 組）。2 つ合わせて f6b0425 比 0.867（5 組）、全体パイプラインでは 0.917。

## 7. リスクと、まだ確かめていないこと

- **ビット一致の前提**：今回の 2 コミットを含め、厳密一致の根拠は IEEE の各演算が同じ順で行われることで、FMA への縮約が起きないこと（x86-64 の既定ターゲット、`-march` なし）が前提。aarch64 の GCC（`-ffp-contract=fast` が既定）では、コードの形が変わると縮約の判断が変わりうるので、その環境では md5 を取り直す必要がある（これは既存の 5 コミットにも当てはまる）。
- **MSVC**：プリフェッチの `_mm_prefetch` の経路はこの環境ではビルドしていない（Windows の Python バインディングの CI で通るはずだが未確認）。
- **734d54f の前提**：葉が 1 点ずつであること（粒度 1）を前提にしている。粒度を変えると、元のコードでも結果が変わる点は同じ。
- **速度の揺れ**：同じビルドでも時間帯で 1〜2 割変わる。比は同じ時間帯の ABAB の中でのみ有効で、4.1 と 4.2 の積が合わない（0.498 と 0.424）のもこのため。
- **確かめていないこと**：ノート PC（4C/8T、SMT あり）での今回の 2 コミットの効果。online_node（実機 ROS）、Humble、他のデータセット、既定で無効な機能（photometric、intensity、kidnap relocalization、relevel、radar、visual）の経路の md5。全体パイプラインで地図保存を有効にした場合。ループ閉じ込みの閾値を緩めてループが実際に採用される場合（exp04 の既定値では 0 件）。MID-360 の速度（md5 のみ確認）。

### 10.3 CPU の取り合いと、バックエンドの積み残し（各 1 回）

`scripts/pipe_drain.sh`：ベンチと同じ launch を起動し、offline_node が終わったあともバックエンドを止めずに、1 秒ごとの CPU 時間を記録した。CPU の使用が 5 秒続けて 0.05 コアを下回った時点を、バックエンドの仕事が終わった時刻とした。

| ビルド | ループ | フロントエンド s | フロントエンドの使ったコア | バックエンドの使ったコア（フロントエンドの動作中） | フロントエンド終了後にバックエンドが働いた秒数 | 両方が終わるまで s（RTF） | バックエンド CPU s | ループ候補（フロントエンド終了時 / 最終） |
|---|---|---:|---:|---:|---:|---:|---:|---:|
| 80f3c1c | 有効 | 188.9 | 1.44 | 2.33 | 17 | 201（1.60） | 492.7 | 16 / 22 |
| f6b0425 | 有効 | 118.3 | 1.61 | 2.33 | 20 | 135（1.07） | 339.7 | 10 / 16 |
| 734d54f | 有効 | 91.6 | 1.60 | 2.35 | 17 | 107（0.85） | 272.8 | 10 / 16 |
| f6b0425 | 無効 | 45.1 | 3.54 | 0.09 | 0 | 45（0.36） | 3.8 | 0 / 0 |
| 734d54f | 無効 | 42.0 | 3.46 | 0.10 | 0 | 42（0.33） | 3.9 | 0 / 0 |

- ループ有効では、バックエンドがフロントエンドの動作中ずっと約 2.3 コアを使い、フロントエンドが使えるのは 1.4〜1.6 コアになる。フロントエンド自身の CPU 時間は大きくは変わらない（f6b0425 で 152 → 182 秒、734d54f で 139 → 141 秒）。遅くなる主な原因は、使えるコアが減ることである。
- 4 コアは飽和していて、両方が終わるまでの時間は「両方の CPU 時間の合計 ÷ 4」にほぼ等しい（例：734d54f は 141 + 273 = 414 CPU 秒で、4 で割ると 103 秒、実測 107 秒）。

- ループ候補 1 回あたりのバックエンドの CPU は約 22〜24 秒（ABAB のランで 446.9 秒 / 19 回、252.8 / 11、223.4 / 10）。フロントエンド終了後まで回したランでは 17〜22 秒（492.7 / 22、339.7 / 16、272.8 / 16）。perf で見ると、バックエンドの CPU の 66% が `pclomp::NormalDistributionsTransform::computeDerivatives`、13% が `pclomp::VoxelGridCovariance::getNeighborhoodAtPoint`、約 8% が OpenMP（libgomp）だった（`data/perf/perf_top_graph_based_slam_loop_on.txt`）。
- **採用されたループは全ランで 0 件**。各ランで評価した候補の fitness の最小値は 1.13〜2.13 で、閾値 1.0 を下回らなかった（`data/pipe_loop/*_loop_candidates.txt`）。最小の 1.13〜1.24 は、フロントエンド終了後まで回したランでだけ出た終盤の候補で、`lidarslam/param/lidarslam.yaml` の閾値（0.7）なら棄却、`graph_based_slam/param/graphbasedslam.yaml` の閾値（1.5）なら採用される値である。

### 10.4 バックエンドの入力の取りこぼし

`scripts/pipe_drain_count.sh`：10.3 と同じ手順でバックエンドが仕事を終えるまで待ってから `/map_save` を 1 回呼び、保存された `trajectory_optimized.tum`（サブマップ 1 個につき 1 行）を数えた。サブマップは「前のサブマップから 1.5 m 以上動いた時点の 1 スキャン」で作られる。フロントエンドの軌跡（1258 スキャン、80.2 m）から計算すると、全スキャンを受け取った場合は 40 個になる。

| ビルド | ループ | サブマップ数 | ループ候補の評価回数 |
|---|---|---:|---:|
| 80f3c1c | 有効 | **34** | 21 |
| f6b0425 | 有効 | **29** | 16 |
| 734d54f | 有効 | **29** | 16 |
| f6b0425 | 無効 | 40 | 0 |
| 734d54f | 無効 | 40 | 0 |

- ループ無効では期待どおり 40 個で、取りこぼしはない。
- ループ有効では 15〜28% のキーフレームが抜ける。バックエンドは単一スレッドのエグゼキュータで、ループ照合はサブスクリプションのコールバックの中で走る（1 候補あたり実時間で 10 秒前後）。その間に届いたオドメトリと点群が、受信の上限（深さ 256）を超えて捨てられていると考えられる（捨てられた場所が DDS の受信履歴か message_filters の同期キューかまでは確かめていない）。例えば f6b0425 では、ループ無効なら bag 時刻 52〜86 秒の間に 10 個あるサブマップのうち、9 個が抜けている（`data/pipe_loop/count_*_trajectory_optimized.tum`）。
- フロントエンドが速いほど、照合で止まっている間に届くデータが増え、取りこぼしも増える（ベース 34 個 → 高速化後 29 個）。ループを有効にして使う場合は、フロントエンドの高速化が地図とグラフの入力を減らす方向にも働く。
- 取りこぼしの有無と量はランごとのタイミングで決まるので、ループ有効時のバックエンドの出力（グラフ、地図）はランごとに変わりうる。フロントエンドの軌跡は全ランで同一。

### 10.5 読み取れること

- ループ閉じ込みを有効にすると、このマシンではバックエンドの NDT によるループ照合が全 CPU の 6 割以上を占め、さらにバックエンドが入力を取りこぼす。フロントエンドの高速化はなお効く（両方が終わるまで 201 → 135 → 107 秒）が、RTF をさらに下げるには、次はバックエンドのループ照合を軽くする必要がある。
- 照合の結果を変えずに速くする余地は、この計測の範囲では確かめていない。結果が変わってよいなら、候補 1 回あたりの NDT の量（照合する点群の密度や反復回数）、評価する候補の数（`loop_search_query_stride`、`search_submap_num`）、NDT のスレッド数を減らしてフロントエンドとの取り合いを避けること、などが調整の候補になる。取りこぼしについては、ループ照合をサブスクリプションのコールバックから別スレッドに出して受信を止めないことが本筋で、受信の深さ（`odom_cloud_sync_queue_size`）を増やすのはその場しのぎになる。どれもバックエンドの出力を変えるので、精度とあわせて評価が必要。

## 12. GLIM に速さで並ぶための追加の高速化（追記、2026-10-17）

lidar_slam_ros2 の報告（11 章）で、同じ VM・同じ終点で GLIM CPU と比べたところ、精度は勝つが速さは負けていた（GLIM 37.84 秒に対し、ループ無効 41.03 秒、ループ有効 45.05 秒）。差のほぼすべてがフロントエンドの処理時間だったので、734d54f の上にビット一致の変更を 2 つ足した。どちらも、exp04 と MID-360 の軌跡の md5 は変わらない（`bc231992…`、`2a1c8107…`）。

### 12.1 採用：d209cb4「Skip the ICP neighbour search when the cached neighbour must still be the nearest」

- 734d54f の perf では CPU の 43% が `get_closest_neighbor` だった。ICP は収束（`dx` < 3e-5）まで反復するので、後半の反復ではキーポイントは mm 以下しか動かない。それでも毎回、近傍 27 ボクセルの点を読み直していた。
- 変更：キーポイントごとの近傍キャッシュに、そのボクセルでの最後の全探索を残す。クエリ q_ref、見つけた点 p、そして q_ref から「p 以外の全点」までの距離の下限 L（読んだ他の点の最小距離と、距離の上限で飛ばしたボクセルの境界の最小値）。同じボクセルでの次のクエリ q について、d = |q − p|、m = |q − q_ref| とし、**d + m + 余裕 < L のときだけ p を返す**（探索しない）。
- 変わらない理由：三角不等式で、p 以外の点はどれも q から L − m 以上離れているので、p は余裕以上の差で真に最も近い点になる。元の探索は、同じ順序・同じ枝刈りでも必ず p を選び、距離 √((p − q).squaredNorm()) も同じ式で計算する。余裕は 1e-6 m + 座標の 1e-12 倍で、比べる値の丸め（座標の 1e-15 程度。点とクエリの差、ボクセル境界、境界上の点がどのボクセルに入るか）より何桁も大きい。同じ距離の点が 2 つあるときは L = d なので省かない（元どおり、探索順で先の点が選ばれる）。
- 全数照合（計測専用の検証ビルド、コミットしていない）：省いたすべての探索で、キャッシュなしの全探索も実行して点と距離をビット単位で比べた。**exp04 で 57,907,507 回、MID-360 で 52,522,575 回、不一致 0**。
- 省けた割合（計装ビルド）：exp04 は近傍探索 6,997 万回のうち 82.8% を省いた（新しいボクセル 5.9%、同じボクセルでの全探索 11.3%）。ICP の連立方程式は 23,353 回（1 スキャン平均 18.6 回）。MID-360 は 6,048 万回のうち 86.8%。
- 単体テスト：`CachedSearchSkipsOnlyWhenTheNearestPointCannotChange` を追加（収束していく 200 本のランダムな歩み、ボクセル内で最近傍が入れ替わる直線の歩み、2 点がちょうど同じ距離になる平面上の歩みで、キャッシュなしの探索とビット単位で比べる）。

### 12.2 採用：a92dfd4「Sum the ICP systems of up to 64 points per reduction task with the same tree」

- d209cb4 の後の perf では、近傍探索は 22% に減り、点 1 つずつのタスク（`parallel_deterministic_reduce` の粒度 1）の負担が目立った（`start_deterministic_reduce`、`fold_tree`、TBB のスケジューリングと待ちで 15% 前後）。

- 変わらない理由：TBB の v2023.0.0 のソースで確かめた。分割は粒度によらず「begin + (end − begin)/2」で、上の段の木は粒度 1 のときと同じになる。どの body も、自分の範囲を処理するときは和がゼロ（右の子は新しい body、左は親の body で、join は葉の後）。葉の中の再帰も同じ足し算を同じ順に行うので、和は粒度 1 のときとビット単位で同じになる。
- 全数照合（検証ビルド）：連立方程式を作るたびに、粒度 1 の元のリダクションでも計算して、H・b・chi・重みの和・対応点数をビット単位で比べた。**exp04 で 23,353 回、MID-360 で 39,572 回、不一致 0**。

## 13. bag の最後で止まる不具合の修正（追記、2026-10-17）

- **症状**：MapsHD HUMANOID-LIO-DATASET の underground-garage の trial-1（rsasaki0109/lidar_slam_ros2 の bench_report 15 章）で、offline_node が終わらなかった。CPU をほとんど使わないまま 25 分止まっていた。

  - 読み込みのスレッドは、LiDAR のバッファが 9 割（45 フレーム）になると、読むのを止めて待つ。

- **出力は変わらない**：時刻順の bag では、45 フレームたまった時点で IMU は先頭のフレームを覆っているので、2 つのフラグのどちらかが必ず立っている。

## 14. 地図の voxel の領域を段階的に確保する（追記、2026-10-18）
