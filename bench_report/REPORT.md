### 指示の手順から変えたところ

- **HILTI exp04 の取得元**：`download_hilti2022.sh` の S3 の URL は `AccessDenied`（403）だった。HILTI の公式ページは Hugging Face（`Hilti-Research/hilti-slam-challenge-2022`）にリンクしているので、そこから同じファイル（10,469,762,246 バイト、sha256 `c650f16f30744d2edff15dcd722a7f21ae0f8868809a3c8863cedd0fc5108799`。スクリプトが記録する raw sha256 と同じ）を、スクリプトが期待する場所に置いてからスクリプトを `--drop-bag1` 付きで実行した。キャリブレーションの zip も S3 で取れないため、Hugging Face の calibration_files の yaml から作った（ベンチには使わない）。変換後の bag は sqlite3、13.46 GB、76,611 メッセージ、長さ 125.814128037 秒、/hesai/pandar 1258、/alphasense/imu 50,198。
- **MID-360**：指示どおり `download_mid360_robot_public_dataset.py` で取得（sha256 `f8f89eeb…` を検証済み）。/livox/lidar 2772、/livox/imu 55,435、277.17 秒。
- **FetchContent の取得元**：GitHub のアーカイブ URL がこの環境では 403 だったため、同じタグを git で取得して `FETCHCONTENT_SOURCE_DIR_*` で渡した（Eigen は gitlab の tarball をそのまま使用）。ビルドのオプションは指示どおり（Release、`-DBUILD_TESTING=OFF -DRKO_LIO_BUILD_ROS=ON -DRKO_LIO_FETCH_CONTENT_DEPS=ON`、テスト用は `-DBUILD_TESTING=ON -DRKO_LIO_BUILD_TESTS=ON`）。ビルドの高速化に ccache を使った（同じ入力から同じ出力を返すだけなので、バイナリは変わらない）。
- **python3**：この VM のイメージは `/usr/bin/python3` が 3.13 だったので、ROS 2 Jazzy に合わせて 3.12 に切り替えた。
- **slam のリポジトリ**：develop（9cc828b、rko_lio サブモジュールは 80f3c1c）。サブモジュールの clone に失敗したので、ローカルの rko_lio から 80f3c1c をそのまま書き出した。Dockerfile と同じく `--packages-up-to lidarslam rko_lio` を Release でビルドし、実行時は rko_lio だけを各計測用ビルド（下記の 80f3c1c・f6b0425・734d54f）でオーバーレイした。`ros2 pkg prefix rko_lio` がオーバーレイ側を指すことを確認済み。
- **単独ブランチ perf/parallel-deskew（f089726）**：積み上げ版の 12cc517 と git の tree が完全に同じ（同じソース）なので、md5 と速度は 12cc517 のビルドで測った。テスト用ビルドは f089726 で別に作って実行した。

### 5.1 バックエンドは律速になっていないか

別に 1 回ずつ、1 秒ごとに各プロセスの CPU 時間（/proc/<pid>/stat）を記録した（`data/pipe/diag_cpu_*.csv`）。

## 6. 追加の高速化（このセッション、f6b0425 の上に 1 変更 1 コミット）

perf（cpu-clock、全スレッド）で f6b0425 を見ると、CPU サンプルの 49% がキャッシュ付きの `get_closest_neighbor` で、その 48% がボクセルの点を読む命令の直後に集中していた（`data/perf/`）。近傍探索ではメモリ待ちが大きいと判断した。

### 6.1 採用：f4a6547「Prefetch the cached voxel points before the ICP neighbour search」

- キーポイントが前回と同じボクセルにいるとき、キャッシュにある近傍ボクセルの点の先頭（最大 3 キャッシュライン、点数に合わせる）を、探索を始める前にまとめてプリフェッチする。
- 変わらない理由：プリフェッチはヒントで、読むボクセル・点・順序・演算は何も変わらない。GCC/Clang は `__builtin_prefetch`、MSVC（x86/x64）は `_mm_prefetch`、それ以外は何もしない。
- 効果：f6b0425 比 0.949（3 組）。プリフェッチ後、点の読み込みでの停止は関数内サンプルの 48% → 14% に減った。

### 6.2 採用：734d54f「Sum the ICP systems in place instead of passing tuples through the tree」

- 決定的リダクションは、6×6 の H・b・スカラー 3 つのタプル（360 バイト）を葉と結合のたびに値渡しでコピーしていた。`parallel_deterministic_reduce` の Body 形式に替え、和を Body の中でその場で足す。
- 変わらない理由：分割と結合の木は同じ（粒度 1 の simple_partitioner で葉は 1 点ずつ）。葉は「ゼロ + その点の系」、結合は「左の和 += 右の和」で、元と同じ足し算を同じ順に行う。対応のない点は何も足さないが、元もゼロを足していただけで、和は +0 から始まり +0 を足しても変わらない（-0 になることもない）。1 点ぶんの系は元と同じ式で作る。
- 効果：f4a6547 比 0.965（3 組）。2 つ合わせて f6b0425 比 0.867（5 組）、全体パイプラインでは 0.917。

## 7. リスクと、まだ確かめていないこと

- **ビット一致の前提**：今回の 2 コミットを含め、厳密一致の根拠は IEEE の各演算が同じ順で行われることで、FMA への縮約が起きないこと（x86-64 の既定ターゲット、`-march` なし）が前提。aarch64 の GCC（`-ffp-contract=fast` が既定）では、コードの形が変わると縮約の判断が変わりうるので、その環境では md5 を取り直す必要がある（これは既存の 5 コミットにも当てはまる）。
- **MSVC**：プリフェッチの `_mm_prefetch` の経路はこの環境ではビルドしていない（Windows の Python バインディングの CI で通るはずだが未確認）。
- **734d54f の前提**：葉が 1 点ずつであること（粒度 1）を前提にしている。粒度を変えると、元のコードでも結果が変わる点は同じ。
- **速度の揺れ**：同じビルドでも時間帯で 1〜2 割変わる。比は同じ時間帯の ABAB の中でのみ有効で、4.1 と 4.2 の積が合わない（0.498 と 0.424）のもこのため。
- **確かめていないこと**：ノート PC（4C/8T、SMT あり）での今回の 2 コミットの効果。online_node（実機 ROS）、Humble、他のデータセット、既定で無効な機能（photometric、intensity、kidnap relocalization、relevel、radar、visual）の経路の md5。全体パイプラインでの地図保存・ループ閉じ込み有効時のバックエンド負荷。MID-360 の速度（md5 のみ確認）。
